# 知识库智能检索工具 产品设计文档

## 背景与痛点

当前知识库对话仅提供基于向量语义检索的单一通路，所有用户提问均经过 Embedding 编码 → 向量相似度计算 → 召回文档片段 → LLM 生成回答。该模式在以下场景存在明确短板：

1. **元信息查询无法满足**：用户询问"知识库有多少合同""最近新增了哪些文件""按类型列出文件清单"等统计类问题时，向量召回返回的是内容片段而非聚合数据，答非所问。
2. **按名定位效率低下**：用户通过文件名（如"帮我找《XX框架协议》的概要"）检索特定文档时，向量检索会对完整 query 编码后在全量切片中匹配，造成不必要的 Token 消耗与较长耗时，且对专有名词的召回率不高。
3. **摘要与条款混杂**：当前 0 号切片（文档概述）与正文条款切片共处同一向量召回池，容易在回答细节问题时被摘要污染，或在查询摘要时被条款内容淹没。

---

## 设计目标

- 将用户对知识库的提问分为三类意图，分别由专属工具高效响应；
- 元信息类查询做到毫秒级、零 Token 消耗；
- 按名定位类查询做到精准快速，直接返回文档摘要与访问链接；
- 语义问答类查询保持当前质量，同时消除摘要对条款召回的干扰。

---

## 用户意图分类

| 意图分类 | 用户典型提问 | 期望响应形式 |
|----------|-------------|-------------|
| 库内元信息查询 | "有多少合同""最近一周新增的文件""按类型分布" | 数量、列表、统计图表 |
| 按名定位 | "《XX 协议》的概要""XX 合同的链接" | 文档名、摘要、访问链接 |
| 按内容语义问答 | "XX 合同关于违约金条款如何约定""甲方是 ABC 的合同有哪些" | 基于条款内容的生成式回答 |

---

## 功能设计

### 一、库内文档元信息查询工具

**功能定义**：以知识库为维度，提供文档数量统计、文档列表查看、按条件筛选等元信息查询能力。

**查询范围**：仅基于文档表的结构化字段（标题、文档类型、状态、创建/修改时间），不涉及 JSON 字段或向量库查询。默认聚合 Agent 绑定的所有知识库，用户可在提问中指定特定库。

**输入参数**：
- 知识库 ID 列表（由会话上下文自动注入，默认为 Agent 绑定的全部知识库）
- 筛选条件（文档类型、创建时间范围、文档状态）
- 分组维度（按月份、按文档类型，可选）
- 分页参数（页码、每页数量）

**输出内容**：
- 符合条件的文档总数
- 文档列表（最多返回 20 条，按修改时间倒序；包含文档名称、文档类型、创建时间、当前状态）
- 超出 20 条时提示"共 N 条，已展示最近 20 条，可进一步筛选"
- 聚合统计（如按类型分布数量）

**核心设计原则**：

> 该工具直接查询数据库完成统计和列表返回，不进入向量检索流程，也不消耗 LLM Token 进行内容理解。
>
> 这样设计是因为元信息类问题的答案完全来自结构化字段（文档名、创建时间、类型等），走向量通路既浪费资源又无法给出准确的数量和列表结果。

---

### 二、文档按名检索与摘要查询工具

**功能定义**：根据用户提供的文档名称，精准定位目标文档并返回其摘要信息和访问链接。

**查询范围**：仅基于文档标题字段做模糊匹配，不查询 JSON 字段。甲方/乙方等非标题属性的查询由语义检索工具通过向量元数据匹配兜底。

**匹配策略**（按优先级依次执行）：
1. 对文档标题进行模糊匹配；
2. 若未命中，向用户反馈"未找到匹配文档"，由 Agent 决定是否转入全库语义检索。

**输入参数**：
- 知识库 ID 列表（由会话上下文自动注入，默认为 Agent 绑定的全部知识库）
- 查询关键词（文档名称）

**输出内容**：
- 文档名称
- 文档摘要（即文档概述内容）
- 文档访问链接
- 文档来源类型、创建时间

**核心设计原则**：

> 文档摘要作为文档自身的描述属性存储于文档表的独立字段中，按名检索时直接从数据库读取返回，无需进行向量召回。
>
> 这样设计是因为文档摘要的本质是"文档级名片"而非"知识级片段"。将其与条款切片分离存储，既能让按名查询高效完成（直接 SELECT），又能避免摘要内容混入条款语义检索池造成召回结果污染。

---

### 三、语义检索工具（现有能力优化）

**功能定义**：保持当前基于向量的语义问答能力不变，针对"按内容理解"类问题进行深度检索和回答生成。

---

## 数据模型变更

### Document 表新增字段

| 字段 | 类型 | 说明 |
|------|------|------|
| summary | Text（可空） | 文档概述摘要，由切片流程中的 0 号切片内容同步写入 |

**变更说明**：新增文档入库时，切片流程生成 0 号切片后，将其内容同步写入 Document.summary 字段。0 号切片暂时保留不做删除，待本方案功能验证通过后再移除 0 号切片的生成逻辑。已有历史数据无需迁移，后续按需补充即可。

---

## Agent 意图路由规则

Agent 系统提示词中需明确以下调度策略，引导 LLM 正确选择工具：

1. 当用户提问包含数量词、时间范围、列表枚举、统计聚合等关键词时，调用「库内文档元信息查询工具」；
2. 当用户提问包含明确的文档名称（书名号、引号包裹或已知文件名片段）、或明确要求查看摘要/链接时，调用「文档按名检索与摘要查询工具」；
3. 其他涉及文档内容理解的问题（包括按甲方/乙方等属性筛选），调用「语义检索工具」；
4. 当「文档按名检索」返回空结果时，自动回退至「语义检索工具」进行全库检索。

---

## 工具调用结果展示

- **列表/统计类结果**：以结构化列表或表格形式呈现，避免 LLM 对数据进行二次复述引入误差；
- **摘要查询结果**：直接输出文档名 + 摘要内容 + 可点击链接；
- **语义问答结果**：保持当前生成式回答格式不变。

## 后续迭代

- 验证方案可行后移除 0 号切片生成逻辑；
- 向量语义检索增加 clause_index != 0 过滤，避免摘要切片干扰条款召回；
- 非合同文档类型的摘要兜底生成（飞书文档取首段、PPT 取首页内容等）；
- 会话级"当前文档"上下文锁定（上一轮定位的文档自动作为下一轮检索范围）；
- 文档别名机制（支持合同简称、内部编号等同义匹配）；
- 甲方/乙方等合同属性的结构化存储（视高频需求决定加独立列或 JSON 索引）；
- 未命中查询的可观测性打点（用于知识库内容补全和同义词扩充运营）。
